# Figma Bridge 讀取設計稿（鐵律）

> 本 skill 是「從 Figma 取得設計資訊」的權威依據。繪製 `.pen` 的規範見 [[pen-authoring]]。
> 較長的走查範例見 [references/walkthrough.md](references/walkthrough.md)。

## 1. 三條鐵律（違反必然做白工）

### 鐵律一：`get_design_context` 只回傳「當前選取」，不是整頁

它回傳的是 Figma 中**當前選取節點**的子樹。**不先 `set_selection` 就呼叫，拿到的是別人上次選取的區塊** —— 內容看起來合理、結構完整，但完全答非所問，而且你不會察覺。

```
✅ set_selection({nodeIds:["1456:126698"]}) → get_design_context({depth:1})
❌ get_design_context({depth:2})            // 範圍未定義，結果不可信
```

**驗證**：`get_design_context` 回傳的 `context[0].id` 與 `context[0].name` 必須是你預期的那個節點。不符就是選錯了，重選。

#### ⛔ 選取是全域共享狀態 —— 多個 agent 同讀一檔時會互搶

**`set_selection` 之後、`get_design_context` 之前，別的 agent 可能已經把選取換掉了。** 你拿到的是**它的**節點，而且內容一樣看起來完整合理。

實測發生過兩次（兩個 `figma-reader` 並行讀同一檔的不同 node）。**這不是理論風險。**

因此上面那條驗證在並行時**不是可選的**：

- **每一次** `get_design_context` 都核對 `context[0].id`，不是只在第一次核對
- 不符 → `set_selection` 重選後再讀一次；**連續兩次都被搶就停下回報**，不要無限重試（那代表有人正在密集操作同一個檔）
- ⚠️ **不要只核對 `name`** —— 同一份設計稿常有多個同名節點（`列表`／`彈窗`），名稱對得上仍可能是別人選的那一個

#### ⛔ 隱藏圖層讀不到 —— 而且它是以「不存在」的樣子消失的

**設計師關掉可見性的圖層，不會出現在任何回傳裡。** 不是帶著 `visible: false` 回來讓你判斷，是**整個節點連同子樹一起消失**，`childCount` 也不計入。

實測（一張後台詳細頁，隱藏了一整個「訂單重要事件提醒」區塊）：

| 工具 | 看得到嗎 | 實測 |
| --- | --- | --- |
| `get_design_context` | ❌ | 父容器 `childCount: 8`、`children` 也是 8 筆，隱藏那塊不在其中；y 座標連續無空位 |
| `get_node` | ❌ | 遞迴全展開整個容器，由上到下 `visible` 全是 `true` |
| `save_screenshots` | ❌ | 算圖本來就不畫隱藏層 |
| **`get_selection`** | **⚠️ 只有「被選取的那一個」** | 直接選取它 → 回傳，`visible: false` 照實給、子樹完整；**選取它的父容器 → 285 個節點全是 `visible:true`，隱藏那塊完全不出現** |

⚠️ **所以 `visible` 這個欄位在實務上等於沒有用** —— 你看到的永遠是 `true`，因為 `false` 的都已經被濾掉了。**「全部都是 `visible: true`」不能推論成「這裡沒有隱藏圖層」。**

**沒有任何程式化的方法可以列舉隱藏圖層。** 唯一途徑是「人在 Figma 圖層面板點它 → `get_selection`」，而 worker 不能向使用者提問 —— 這條路只有主控端走得通（見 [[design-lead]]）。

**這件事真正的代價不是「多讀到東西」，是「少讀到東西而沒人知道」**：設計師常用「一張畫面 ＋ 隱藏區塊」表達狀態差異，於是那個區塊、以及它背後「什麼情況才顯示」的業務規則，會從分析檔、規格到資料表設計整條鏈一起消失，而每份文件看起來都很完整。因應作法見第 7 節。

### 鐵律二：`get_node` 對大型 Section 會吐出數百萬字元

單一 Section 展開後可達 800 萬字元，遠超 token 上限，結果被丟到檔案裡，等於白呼叫。

**正確作法**：`set_selection` + `get_design_context({depth:1})`，看到 `childCount` 就換下一層的 id 再 depth:1，**逐層下探**。`get_node` 只用在明確的小節點（單一 text、單一 instance）。

### 鐵律三：`get_screenshot` 回傳 base64，會爆 token

即使 `scale:0.09` 也可能 60 萬字元。**一律改用 `save_screenshots` 存檔，再用 `Read` 讀圖。**

```
save_screenshots({items:[{nodeId:"1399:258854", outputPath:"<專案內路徑>/x.png", scale:1}]})
→ Read(file_path:"<專案內路徑>/x.png")
```

- `outputPath` **必須在 MCP server 的工作目錄（＝專案根目錄）內**，指到系統暫存目錄會被拒絕。
- 用專案內暫存夾（如 `.tmp-figma/`），**任務結束一定要刪除**，不要污染專案。
- 存檔會回傳實際 `width`/`height`，可用來確認尺寸。

## 2. 起手式

```
list_files()                         // 確認連著哪些檔，取得 fileKey（見 2.1）
get_metadata({fileKey})              // 確認檔名、目前頁面、所有頁面清單
set_selection({nodeIds:[目標id], fileKey})   // 界定範圍（鐵律一）
get_design_context({depth:1, fileKey})       // 取結構
```

**從 URL 取 node-id**：`?node-id=1456-126698` → **把連字符換成冒號** → `1456:126698`。
工具的 `nodeId` 只接受冒號格式（`^(\d+:\d+|I\d+:\d+(;\d+:\d+)+)$`），用連字符會被 schema 擋下。

### 2.1 多檔連線：`fileKey` 一律帶，且一律先查

bridge 可以同時連著多個 Figma 檔（一個檔一條連線）。因此：

- **`list_files()` 是起手第一步**，回傳每個已連線檔的 `fileKey` ＋ `fileName`。
- **之後每一支呼叫都帶 `fileKey`**（`get_metadata`／`set_selection`／`get_design_context`／`get_node`／`get_variable_defs`／`save_screenshots` 全部）。多檔連線時它是**必填**，不是選用。

⛔ **連線不是你能建立的。** 連線由**每個 Figma 檔裡各自跑的 plugin** 主動連上 bridge，`list_files` 只列出「已經連上的」。目標檔沒出現在清單裡，就是使用者還沒在那個檔裡開 plugin —— **停下回報請他開，不要找別的檔湊合**。

⚠️ **只連著一個檔時，帶錯的 `fileKey` 不會報錯。** 單檔情境下 bridge 會回退到那條唯一連線，於是你**照樣拿得到內容完整、看起來合理的結果，只是那是另一個檔的**。所以核對要在 `list_files` 那一步做完：

- 派工給的是 `fileKey` → 確認它出現在 `list_files` 的回傳裡。不在就停下回報，**不要因為「反正只連一個檔、應該就是它」而硬跑**。
- 派工給的是**檔名** → 用 `fileName` 比對取得 `fileKey`。**比對不到、或比對到多筆（同名檔）就停下回報**，不要挑一個最像的。

**同一個工作階段裡讀多個檔時，每次切換目標檔都要重新核對一次** —— `fileKey` 打錯一個字元的症狀，跟「這個檔本來就長這樣」完全一樣。

> 這也改變了鐵律一那條「選取被搶」的風險範圍：**選取是「每個檔各自」的全域狀態**。兩個 reader 讀**不同檔**不會互搶；讀**同一個檔**才會，那時鐵律一的重選與停工規則照舊適用。

## 3. 取得中文內文（設計稿的關鍵資訊都在這）

`get_design_context` 為了控制大小，**深層節點的子樹會被截成 `childCount`**，thead 的欄位標題、按鈕文字、彈窗內文、便利貼內容全都在被截掉的那一層。

**要拿文字，就對該節點單獨 `save_screenshots` 放大讀圖**：

| 目標 | 建議 scale |
| --- | --- |
| 整個 Section 總覽（看流程排列） | 0.09 – 0.3 |
| 單一畫面（1280 寬） | 1 |
| 便利貼／註解 | 1 |
| 表格 thead（要讀欄位名） | 1.5 – 3 |

> 讀圖比猜結構可靠得多。**寧可多截幾張圖，也不要臆測欄位名稱。**

## 4. 設計稿的色彩語意（本工作區的 Figma 慣例）

判讀註解時，顏色就是分類：

| 顏色 | 色碼 | 意義 | 處理方式 |
| --- | --- | --- | --- |
| 紫色便利貼 | `#763dd8` | **設計規則／業務邏輯**（權威） | **逐字引用**，不要改寫 |
| 淺藍區塊 | `#ccf3ff` / `#f4fbff` | 情境說明、名詞筆記 | 逐字引用 |
| 粉紅／橘色便利貼 | `#f8b6a8` 系 | **待討論的設計疑問** | 挑出來獨立標註，不要當成已定案 |
| 紅字 | `#eb4751` 系 | 建議事項、風險提示 | 挑出來獨立標註 |
| 藍色帶 | `#3065aa` | Section 標題帶 | 流程分區的依據 |
| 灰色帶 | `#a7abac` | 步驟標題（sub_unit） | 步驟名稱的來源 |
| 連接線 | `#a2d1e3` | CONNECTOR，流程走向 | 判讀步驟順序 |

## 5. 判讀流程排列

Figma 的流程稿慣例：**由上而下是階段，由左而右是步驟**。

- 最外層 SECTION = 功能（例：`採購作業-進貨作業`）
- 第二層 SECTION = 階段（列表頁／新增／編輯／刪除）
- 灰色 `sub_unit` 帶 = 該階段內的步驟名稱
- `CONNECTOR` 節點 = 明確的流程連線，優先採信它而不是座標推測
- 名稱含 `mask` + `popup-L` / `dialog` 的組合 = 彈窗畫面（底畫面＋遮罩＋彈窗）

## 6. 量測版面與色票（分析檔第 9 節的資料來源）

畫面結構與欄位文字回答「有什麼欄位」，**第 9 節回答「長什麼樣、由什麼組成」**。沒有它，下游 `pen-drawer` 只能自己編色票、並照繪製 skill 的示意值補元件（見 [[design-handoff-contract]] 第二節「為什麼第 9 節非有不可」）。

第 9 節有兩種性質不同的資料，**量法也不同**：

| 小節 | 回答什麼 | 怎麼取 |
| --- | --- | --- |
| **9.0 元件組成與呈現方式** | 有沒有這個東西、是哪一種形式 | 展開節點樹**逐項清點**（見 6.6） |
| 9.1～9.4 色票／骨架／對齊／差異 | 什麼顏色、多大、怎麼排 | 讀節點屬性（見 6.1～6.5） |

### 6.1 可靠度階層：讀屬性 ＞ 截圖取樣 ＞ 目視形容

| 方法 | 可靠度 | 失效模式 |
| --- | --- | --- |
| **讀節點屬性**（`get_node`／`get_variable_defs`） | 最高 | 拿錯節點（可自檢：核對 `name`） |
| 截圖取樣色碼 | 中 | 反鋸齒、疊加透明度、縮放插值都會讓取到的值偏掉幾階 |
| 目視描述（「深藍」「靠左」） | 最低 | 實測把「淺灰側欄＋深藍橫幅」看成「深藍側欄」，完全相反 |

⛔ **色值與尺寸一律讀屬性，不要用截圖目視填。** 截圖的用途是**定位該量哪個節點**，不是取值。

### 6.2 工具分工

| 要什麼 | 用什麼 |
| --- | --- |
| 色票、間距、圓角的**設計變數** | `get_variable_defs`（先 `set_selection` 界定範圍）—— 有變數就記變數名，比記色碼更耐改版 |
| 單一小節點的完整屬性（填色、邊框、尺寸、圓角、字級、內距） | `get_node` |
| 容器層的排版屬性（direction／gap／對齊） | `set_selection` ＋ `get_design_context({depth:1})` |
| 樣式（若設計稿用 Figma styles 而非 variables） | `get_styles` |

> 屬性的**實際欄位名以回傳為準**（各版本 Figma 與 bridge 的命名不完全一致）。找不到某個屬性時**寫「未量到」並註明找過哪裡**，不要換算或猜。

#### ⚠️ `get_design_context` 逾時就換 `get_node`，不要反覆重試

實測遇過：`get_design_context` 對某個元件實例**連 `depth: 1` 都持續回「Unable to establish connection to Figma after 10 seconds」**，
而**同一時間** `get_metadata`／`save_screenshots`／`set_selection` 全都正常。

**那不是連線斷了，是這支工具對該節點卡住。** 訊息長得像網路問題，會讓你去重試或放棄，兩個都是錯的動作。

```
get_node({ fileKey, nodeId: "1461:191396" })    // ← 一次就通，且直接回兩層子節點
```

| 情況 | 用哪支 |
| --- | --- |
| 要看某節點的**子節點清單**、逐層下探 | `set_selection` ＋ `get_design_context({depth:1})` |
| **只要一個節點（含它的子節點）的完整屬性** | **`get_node`** —— 不必先 `set_selection`，也不受上述卡住影響 |
| 前者逾時 | 直接改後者，**不要重試第三次** |

### 6.2.1 ⛔ 先畫容器樹，再填數值（順序不可顛倒）

**量版面的第一步不是量數字，是把容器階層走出來。** 從畫面根節點開始 `depth:1` 逐層下探，
把「誰包誰、每層幾個子節點、每層的 gap 與 padding」記成一棵樹，**再回頭填各元素的尺寸**。

⛔ **顛倒過來做（先量元素、再湊階層）必然漏層。** 那些「只是把兩張卡包在一起」的中介容器
在視覺上完全看不出來 —— 它沒有底色、沒有框線、寬度與子節點一樣，**唯一的存在證據就是它的 `gap`**。

實測代價：漏掉一層 `gap 0` 的群組容器，下游把兩張卡當成內容區的平行子節點、套用內容區的 `gap 24`，
單這一項就多 24px；同一畫面另一處卡片內容 gap 20 被當成 24，再多 4px。**28px，而下游查不出是哪一項。**

**自檢**：容器樹走完後，用它把畫面總高算一次，與 9.4 記的畫面高度對。**對不上就是還有一層沒走到**，
不要用「大概是捨入誤差」帶過 —— 這個算式是全對或全錯，不會差幾 px。

### 6.2.2 ⛔ `fills` 是堆疊陣列，`fills[0]` 不是「這個節點的顏色」

**Figma 的 `fills` 由下往上堆疊，最後一個蓋在最上面。** 讀 `fills[0]` 拿到的是**最底層**的，
而它可能被完全遮住 —— **你會得到一個真實存在、但畫面上根本看不到的顏色**。

> **實測**：某個合計區的 `fills` 是 `[{#eef0f0}, {#f4fbff}]`，畫面上是 **`#f4fbff`（淺藍）**。
> 讀 `fills[0]` 得到 `#eef0f0`（灰白），寫進分析檔、下游照著畫 —— **顏色錯了，而每一道檢查都是綠燈**
> （值是真的、來源 node id 是對的、與分析檔完全一致）。使用者一眼就看出來了。

**取色的正確作法**：

```python
def color(styles):
    fs = styles.get('fills')
    if not isinstance(fs, list): return None          # 可能是字串 "mixed"
    solid = [f for f in fs if isinstance(f, dict) and f.get('visible', True) is not False]
    if not solid: return None
    if len(solid) > 1:
        return ('多層', [(f.get('color'), f.get('opacity')) for f in solid])  # ⛔ 停下來人工判斷
    return solid[-1].get('color')                      # 單層時取最後一個
```

| 情況 | 怎麼處理 |
| --- | --- |
| 一層 | 直接取 |
| **多層** | ⛔ **不要自動取最上層就算了** —— 上層若有 `opacity < 1` 或 `blendMode` 不是 `PASS_THROUGH`，實際顏色是混合結果。**匯圖取樣驗證**，並在分析檔註明「多層 fills，實際值由取樣得出」 |
| `fills` 是字串 `"mixed"` | 該節點分段上色，節點資料讀不到 —— **匯圖取樣**（見 6.1 的可靠度階層例外） |
| 陣列裡有 `visible: false` 的層 | 略過那一層 |

⚠️ **這種錯在整批量測裡只會出現少數幾個**（實測 1110 個有 `fills` 的節點只有 3 個是多層），
所以**不會有任何統計異常**，只能靠取值程式本身寫對。**寫掃描程式時就把多層判斷放進去，不要事後補。**

### ⛔ 對齊值要逐畫面量 —— 在「內容剛好填滿」的畫面上量它，等於沒量到

`primaryAxisAlign`／`counterAxisAlign` 這類屬性**只有在「內容比容器小」時才顯現**。
挑一張內容填滿的代表畫面去量，會得到一個**值是對的、但沒被驗證過**的數字。

> **實測**：列表頁的分頁群組 `Pagination_group`，
> 在 **L-A 是 964×24**（10 列資料，卡片被表格撐滿，群組剛好包住頁碼列）；
> 在 **L-C 是 964×293**（1 列資料，卡片仍固定 504 高）—— 而它的 `counterAxisAlign` 是 **`MAX`**，
> 頁碼列因此**貼在群組底部**（實測頁碼在 y=269 ＝ 293−24）。
>
> **設計意圖是「表格卡高度固定，資料少時分頁列仍貼在卡片底部」。**
> 分析檔只量了 L-A（群組 24 高、`MAX` 看不出效果），把它當成通則；
> 下游照著畫 L-C，分頁列緊貼表格，整塊內容再被卡片的對齊往下推 ——
> **表頭從 y=328 掉到 464，與查詢區之間空出一大片。**

⛔ **最危險的是那條佐證**。reader 在表格卡那列寫了「無多餘空間，`CENTER` 不產生位移」——
那句話在 L-A 為真，於是下游**沒有任何理由懷疑這一整組值**。

| ❌ 這樣寫 | ✅ 該這樣寫 |
| --- | --- |
| 無多餘空間，CENTER 不產生位移 | ⚠️ **本畫面內容剛好填滿，看不出對齊效果 —— 這個值未經驗證，資料量不同的畫面要另外量** |

**規則**：

1. **凡是「內容量會變」的容器**（列表卡、表格卡、任何裝可變筆數的東西），
   **至少量兩張**：一張內容多的、一張內容少的
2. 值不同就寫進 **§9.4 逐畫面差異**，不要當成通則
3. 佐證寫「本畫面看不出效果」而**不是**「不產生位移」——
   前者提醒下游還要驗，後者讓下游放心

> 這與下面 6.2.x 的「`padding` 只是最小留白，位置由對齊決定」同一族：
> **屬性的效果取決於內容與容器的相對大小**，量的那張剛好看不出來時，值就沒被驗證過。

### ⛔ padding 記了不等於位置就對了 —— 內容比可用空間大時，是「對齊」在決定位置

Figma 的 auto-layout：`padding` 只是**最小留白**。當內容尺寸超過「容器 − padding」時，
內容會溢出，而**實際位置由 `counterAxisAlign`／`primaryAxisAlign` 決定，不是由 padding 決定**。

> **實測**：頂欄 50 高、`padding top 10`、內容 36 高。
> 可用高只有 30 < 36，所以 padding 沒起作用 —— 內容依 `counterAxisAlign: CENTER`
> 落在 **y=(50−36)/2＝7**。下游照字面套 `padding top 10` 畫，整排內容**偏下 3px**。

**記進分析檔時，padding 與對齊要一起記**，並附一條算式說明實際位置是哪個決定的：

```
內容 Frame @(20, 7)  ← 7 = (50 − 36)/2，counterAxisAlign CENTER 決定；padding top 10 未生效
```

⚠️ **驗法**：拿 `padding` 算出來的位置與節點回傳的 `bounds.y` 對一次。
**對不上就是對齊在主導** —— 而 3px 這種差距在畫面上看不出來，只有量才知道。

### ⛔ 註解要以「Figma 全檔的 Notes 節點總數」對帳，不要以 SECTION 為單位

實測漏收了一則註解，而且**是用 SECTION 當單位檢查所以查不出來** ——
那個 SECTION 在分析檔第 6 節連一列都沒有，「每個 SECTION 都有收到嗎」這個問題**根本不會被問到它**。

⛔ **收註解時，node id 欄要填註解本身的 id，不要填「`{SECTION id}` 內」。**
只記到 SECTION 層會有兩個後果：同一個 SECTION 有多則時分不出是哪一則，
以及**沒有任何一則的 SECTION 就整個從清單上消失**。

**對帳方法**（機械可判）：

```
遍歷整份文件，數以下兩類的最外層節點  →  N
  ① type=INSTANCE 且 name 含 "Notes/"
  ② type=WIDGET          ← 另一種註解形式，不要漏
分析檔第 6 節的資料列數  →  M
N == M 才算收齊
```

⚠️ **註解不只一種形式。** 實測第三份稿有 25 則 `Notes/` ＋ **15 個 `MarkNote` widget**，
兩種都是設計師寫的說明。⛔ **只數 `Notes/` 會漏掉 15 則，而對帳還會顯示通過。**
開工前先掃一次「這份稿有哪些型別的節點帶文字說明」，不要假設只有一種。

⚠️ 這比「每個 SECTION 都看過了」可靠 —— **後者的漏網之魚剛好是「你沒想到要去看的那個」**。

### 6.2.6 ⛔ 用像素驗證時，不要用「顏色**等於**某個色碼」當條件

陰影、半透明遮罩、疊在上面的浮層都會把底下的顏色**等比改掉**，而值仍然是「一個顏色」——
不會有錯誤，只會讓等值比對整段落空。

> **實測兩例**：
> ① 凍結欄的外陰影（`offset x:-8, blur:15`）把左側 23px 內的底色壓暗
> （`#dfe4e5`→`#ccd0d1`、`#00a59b`→`#009a91`），等值比對判成「這裡沒有框線」，
> 於是推論出「欄寬從 116 變成 100」—— **而 100 ＝ 84 ＋ 內距 16，看起來還特別合理**。
> ② 彈窗畫面上有全螢幕遮罩，`#dfe4e5` **一個像素都不會出現**，
> 直接比色碼會得到「0 條線」，看起來就像根本沒畫。

**改用其中一種**：

| 作法 | 適用 |
| --- | --- |
| **從一條已知存在的框線取樣**，拿它當該畫面的參考色再掃 | 有遮罩／整體調色時。首選 |
| 容差比對（各通道差 ≤ 8） | 半像素造成的邊緣混色 |
| 比對「與相鄰列不同」而非「等於某色」 | 只想知道線在不在、不在意色碼 |

⚠️ **半整數座標會讓 1px 線渲染成兩排混色**（實測彈窗 `y=81.5` 使框線變成 `#eff1f2`／`#e1e1e3`）。
看到這種成對的淺色時，先查該節點的 y 是不是 `.5`，**不要當成線畫錯了**。

### 6.2.5 ⛔ `strokeWeight: "mixed"` ＝ 只有部分邊有框線 —— 要逐邊確認

`get_node` 對這種節點只回一個字串 `"mixed"`，**不會告訴你是哪幾邊**。

**驗法是取像素**：匯出該節點，看它上／下／左／右四條邊的色碼是不是框線色。

> **實測**：表格資料列的每個 `tbody` 儲存格都是 `strokeWeight: "mixed"`。
> 用像素掃才確認出「四邊都有，只有操作欄那格整格沒有」——
> 而分析檔當時寫的是「操作欄無**右**框線」，把「整格沒有」寫成了「少一邊」。

⛔ **框線常常由「多個層級各畫一部分」組成 —— 要問「這條線是誰畫的」，不是「這一格有沒有框」。**

> **實測**：表格的線分屬三個層級 ——
> **列容器**畫底邊（橫貫全寬）、**儲存格**畫右邊（分欄）、**表格容器**畫四周外框。
> 只查儲存格屬性會得到「操作欄整格無框線」這個**對於該節點為真、對於畫面為假**的結論
> ——那格的 `strokes` 確實是空陣列，但它底下的線是列容器畫的。

⚠️ **這種錯誤在數字上完全對得上**：把線全歸給儲存格（右＋底）算出來的橫線數量一條不差，
**只有在「唯一沒有儲存格框線的那一格」才露餡**。
所以驗證要**掃那一格所在的欄**，不要只掃資料欄。

⚠️ 記進分析檔時**寫通則再寫例外**（「每格四邊 1px `#dfe4e5`；操作欄該格整格無框線」），
不要只寫例外 —— 只寫例外的話，下游得反推通則，而**反推只會推出其中一個方向**。

### 6.2.4 ⛔ 子節點會把父節點的 `fill` 與 `stroke` 完全蓋住

6.2.2 講的是**同一個節點**的 `fills` 堆疊。這一條是**不同節點之間**的疊層 —— 更常見，也更難察覺。

> **實測**：側欄第一層項目的 `Accordion` 節點 `fills` 是 `#eef0f0`，我照抄進色票。
> 但它底下還有一個滿版子節點 `Frame 2431`，`fills` 是 `#f4f4f4` ＋ 1px `#d7d7d7` 底框 ——
> **畫面上看得到的是 `#f4f4f4`，`#eef0f0` 一個像素都露不出來。**
> 下游照色票畫，五個選單項目全部錯色、五條分隔線全部沒有。

**量容器的顏色時，先確認它有沒有滿版子節點**：

| 子節點 | 父的 fill／stroke |
| --- | --- |
| 尺寸等於父（扣掉 padding 後仍滿版）且不透明 | **完全看不到** —— 要記的是子節點的值 |
| 比父小，或有 padding 露出邊 | 父的值是背景色，兩個都要記 |

⚠️ **驗法：抓一個「一定在該區塊內、但不在任何文字上」的像素點，比對你記的色碼。** 對不上就是被蓋住了。
只看節點資料永遠發現不了 —— 兩個值都真實存在，只是其中一個看不到。

### 6.2.3 ⛔ 節點資料與渲染結果不一致時，以渲染為準 —— 但要找出原因

`fills` 多層、`fills: "mixed"`、`opacity`、`blendMode`、被上層節點遮住 —— 這幾種情況都會讓
**「讀到的值」與「看到的顏色」不同**，而讀到的值本身是真的。

判準：**量完之後，把該區塊匯圖取樣抽驗幾個關鍵色**。對不上就回頭找是上面哪一種，
⛔ **不要以「節點資料比較可靠」為由忽略取樣結果** —— 6.1 的可靠度階層講的是「不要用截圖取代量測」，
不是「量測到的一定就是看得到的」。

> 取樣時 ⚠️ **PNG 有 alpha，轉 RGB 會把透明背景變成黑色並污染統計**。
> 用 RGBA 並**只取 `a >= 250` 的像素**。實測不這樣做會得到一個被壓暗約 25% 的假色值。

### 6.3 量對齊：一定要算偏移，不能看子節點順序

**Figma 的 auto-layout 下，子節點順序與視覺位置沒有必然關係。** 「第一個子節點＝在左邊」這個推斷不成立 —— 實測就是這樣把一列**置中**的頁碼群記成「左側」，害下游 13 條分頁列全部畫成靠左。

判定方式固定成算式，不留解釋空間：

```
子節點中心 = x + width / 2
容器中心   = 容器.x + 容器.width / 2
兩者差 ≤ 2px → 置中；子節點.x ≈ 容器.x → 靠左；右緣對齊 → 靠右
```

寫進第 9.3 節時**要把算出來的偏移值一起寫**（例：`頁碼群 x=556、寬 388、中心 749；容器中心 750 → 置中`）。

### 6.3.1 ⛔ 量到的值不等於生效的值 —— `gap` 尤其

**`gap` 只有在父容器有 2 個以上子節點時才看得出效果。** 只有一個子節點時，`gap` 照樣讀得到一個數字，
但那個數字在畫面上**從來沒有作用過** —— 你把它寫進分析檔，下游會忠實套用，然後整份稿的節奏就跑掉。

實測案例：分析檔記「卡片內容區 gap 20」，來源是訂單資訊卡的內容容器（它的 gap 真的是 20）。
但那張卡的內容容器**只有一個子節點**；其餘四張卡的資訊列容器實際都是 `gap: 0`（列高 48 已含間距）。
下游套用 20 之後每張卡多出 `(列數−1)×20`，**列數越多差越大**（+80／+60／+40／+20／+0），
於是卡與卡之間的 24 明明是對的，畫面看起來卻是「每張卡上下節奏都不一樣」。

**判準寫成機械的**：

| 情況 | 怎麼記 |
| --- | --- |
| 父容器子節點 ≥ 2 | 照讀到的值記 |
| 父容器子節點 ＝ 1 | ⛔ **不要記那個 gap** —— 記「單一子節點，gap 不生效」，並去量另一個同類容器 |
| 值要寫成通則（「卡片內容區 gap」這種） | **至少抽驗 2～3 個實例**；各實例不一致就逐一列出，不要挑一個當代表 |

> 同一條也適用於 `padding`、`justifyContent`、`alignItems` —— 單一子節點時 `justifyContent` 的差異也看不出來。

### 6.4 量寬度要量容器 frame，不要量文字節點

文字節點的 bounds 含反鋸齒與行高留白，量出來會比視覺寬度多出幾 px。**要量的是包住它的 frame。**

### 6.4.1 「同一種東西」不一定同一組數值 —— 逐個量

⛔ **同一個元件的不同「態」也算不同的東西。** 實測側欄第一層選單：
**展開態**是 `#eef0f0`、無邊框；**收合態**是 `#f4f4f4` ＋ 1px `#d7d7d7` 底框。
只量到其中一個就套用全部，畫面上會有一半是錯的 —— 而錯的那一半看起來仍然很整齊。

實測：列表頁表格的表頭高是 **45**，訂購商品明細的表頭高是 **66** —— 都是「表頭」，差 21。
分頁列的頁碼是 **24×24 圓角 4 的 instance**（當前頁還有藍底白字的高亮態），不是文字符號。

⛔ **不要因為「這也是個表格／也是分頁列」就沿用先前量到的值。** 每一種各量一次，寫進 9.2 時把**用在哪裡**一起寫（例如「表頭高（列表頁）」vs「表頭高（商品明細）」）。

### 6.4.2 量文字：把畫面上所有 TEXT 節點抓出來「依屬性分群」，不要自己分級

⛔ **不要先想「這頁有哪幾級文字」再去量** —— 那是先有結論再找證據，併錯與漏掉都不會留下痕跡。

**正確做法是反過來**：把該畫面底下**所有** `TEXT` 節點連同 `fontSize`／`fontWeight`／`fontFamily`／`fills` 一次抓出來，
**依這四個屬性分群**，每一群就是一種文字元素。群的數量是量出來的，不是你決定的。

實測一次分群結果（同一張列表頁）：

```
24px/700  訂單維護（頁標題）          18px/500/#ffffff  集團形象商品訂購平台
18px/500  側欄 L1 ×6                 16px/400/#494a57  側欄 L2 ×6
16px/400/#ffffff  管理者 (暫時)       14px/500/#ffffff  登出、上傳訂單、查詢、表頭 ×7
14px/400/Roboto   表格數字、頁碼      14px/400/NotoTC   表格中文、下拉值
14px/400/#aeafb4  請輸入              14px/400/#494a57  共10頁 100筆
14px/500/#0093c1  清除
```

**13 群 = 13 種文字元素**。而該份分析檔只記了 **5 個「級別」** —— 差的 8 種在下游全部變成 14px。

⚠️ **同樣的內容不代表同一種元素**：`訂單維護` 在這頁出現三次（頁標題 24/700、側欄 L2 16/400、表格內文 14/400）。
**依屬性分群才分得開，依文字內容或憑印象分級一定會併錯。**

⚠️ **數字與中文常常不同字型**（實測數字是 `Roboto`、中文是 `Noto Sans TC`），分群時它們會自然落在兩群，
**這正是分群法的價值 —— 你不會事先想到要分這一刀。**

### 6.4.3 ⛔ 文字要連「寬度模式」一起量，不只是字級與顏色

`textAutoResize` 決定文字**會不會換行**，而它在分析檔裡幾乎總是被漏掉 —— 只記了字級、字重、顏色。

| Figma 的值 | 意思 | 下游要畫成 |
| --- | --- | --- |
| `WIDTH_AND_HEIGHT` | **hug**，依內容決定寬高，**永不換行**（放不下就溢出容器） | 文字**不設寬度**，對齊交給父容器的 `justifyContent` |
| `HEIGHT` | 寬度固定、高度自動 → **會換行** | 文字設固定寬或 `fill_container` |
| `NONE` | 寬高都固定 → 超出會被裁切 | 兩者都固定 |

⚠️ **設計稿裡「文字比可用空間寬」是常態，不是錯誤。** 實測一張表格有兩格在 Figma 本來就溢出 padding
（`5.76折` 42 > 可用 38、表頭 `折扣金額` 56 > 可用 53），儲存格 `clipsContent: false` —— **設計稿就是讓它壓進 padding 裡**。
下游若把文字畫成鎖寬，這兩格就會換行，**行高變兩倍、整列跑版**。

**量的時候順手記**：`textAutoResize`、父容器的 `clipsContent`、以及「文字寬 vs 容器可用寬」有沒有溢出。
⛔ 溢出時**不要縮小字級或加寬欄位去「修正」** —— 那是設計稿的事實，照抄。

### 6.5 先量共用元件

Navigation、header、表格框架這類**被多張畫面引用**的元件要優先量準：一次量錯 ＝ 整批畫錯（實測 10 張畫面全中）。反過來說，修的時候也只要改那一個元件。

### 6.6 量「元件組成與呈現方式」（第 9.0 節）：清點，不是取值

9.1～9.4 量的是數字，**9.0 量的是「有沒有」與「是哪一種」** —— 沒有數字可讀，只能展開節點樹逐項清點。

**做法**：`set_selection` 選中該區塊 → `get_design_context({depth:2})` 看它的直接子節點清單 → 逐項對到 9.0 的五類。

| 要清點的 | 具體做法 | ⛔ 常見的錯 |
| --- | --- | --- |
| 頂欄放什麼 | 展開頂欄 frame，把每個子節點逐項記下來（含 icon 節點） | 只記「頂欄」三個字就過去了 |
| 側欄層級與選取態 | 比對選中項與未選中項的節點差異（多一層底色 frame？多一條色條？） | 只記「側欄有選單」 |
| 按鈕有沒有 icon | 展開按鈕實例，看子節點裡有沒有 `VECTOR`／icon 型節點 | 假設按鈕都長一樣，只查一顆 |
| 操作怎麼呈現 | 看設計稿有沒有該操作的獨立畫面稿（＝換頁）、有沒有遮罩＋對話框（＝彈窗）、有沒有側滑面板（＝抽屜）；配合第 5 節流程與 `CONNECTOR` 判 | 憑「後台系統通常是換頁」推斷 |
| 列表列操作區 | 展開任一列的操作儲存格，逐項記 | 記成「有編輯刪除」，漏掉它其實是一顆「⋮」下拉 |

**每一項都要寫「無」或實際內容，不留空。** 空白與「這裡沒有東西」在下游眼中一樣，
而**「沒填」會被當成「可以自己看著辦」** —— 實測後果就是稿上沒有的 icon 被加了進去。

> **為什麼要特別清點「按鈕有沒有 icon」這種小事**：下游繪製 skill 為了給範例，難免帶著示意寫法。
> 9.0 沒寫時那些示意就成了預設答案，而多加一顆 icon **不會破版、不會報錯、自我檢查全綠**。

## 7. 忠實回報，不要順手「修正」設計稿

設計稿常有複製未改的殘留（標題寫錯、筆數對不上、狀態不一致）。**這些是發現，不是錯誤處理對象。**

- 照原稿理解，**把矛盾挑出來回報給使用者**，由使用者決定。
- 同一份稿裡出現互相矛盾的敘述時，**三處都引用出來**，不要自己選一個。
- 規格元件（`table-title-*` / `table-content-*`）與實際畫面不一致時，兩邊都要記錄。

### 7.1 ⛔ 但「複本之間區塊有無」是例外：登記為狀態差異，不要寫成設計疑問

同一畫面的多個複本（列表／編輯／查看、各種訂單狀態…）之間，**某個區塊在 A 有、在 B 沒有** —— 這種差異**預設不是矛盾**，寫進**第 9.4 節「逐畫面差異」**，不要升級成第 7 節的設計疑問。

**理由是你根本無從判斷。** 設計師表達「這個狀態不顯示這塊」的標準作法就是複製畫面再隱藏區塊，而隱藏圖層在你眼中是**不存在**（見鐵律一底下那節）。所以「B 少一塊」有兩種可能，**而你看到的東西一模一樣**：

| 實際情況 | 你看到的 |
| --- | --- |
| 設計師隱藏了它（刻意） | B 沒有這塊 |
| 設計師忘了畫（缺陷） | B 沒有這塊 |

把它寫成疑問的後果是實測過的：每一個複本差異都變成一張要使用者裁決的疑問卡，而**多數沒有答案可給** —— 使用者只能回你「那是隱藏的」。

**措辭要跟著改**：

- ✅ 「複本 B 未出現『退款資訊』區塊（A 有，node id `xxx`）」
- ⛔ 「B **缺少**退款資訊區塊」／「疑似**漏畫**」 —— 這是在陳述一件你無法確認的事

**什麼時候才升級成疑問**：該區塊的有無會**影響資料模型或流程**（例如 B 少的是一整組會落到資料表的欄位），此時照第 7 節三要素寫，並在影響欄註明「亦可能為隱藏而非缺漏，需人工確認」。

**要確認到底是哪一種**：請主控端要使用者在 Figma 圖層面板選取該圖層，再跑 `get_selection` —— 那是唯一讀得到隱藏內容的路徑。你不能自己要求（worker 不能 `AskUserQuestion`），**在回報中列出「建議人工確認的區塊」即可**。

## 8. 常見錯誤對照

| 症狀 | 原因 | 解法 |

| 回傳被存到檔案、超 token | 用了 `get_node` 展大節點 | 鐵律二，改逐層 depth:1 |
| 截圖爆 token | 用了 `get_screenshot` | 鐵律三，改 `save_screenshots` |
