# Pen 共用元件庫繪製

> 共用基礎（工具總覽、`execute` 作用域、Copy／descendants、驗證）見 [[pen-authoring]]，**先遵循它**。
> 本技能只補「共用元件庫」這種**以分類陳列元件本身**的場景。畫系統畫面見 [[pen-screen-drawing]]；畫流程摘要見 [[pen-flow-diagram]]。
> 元件庫與 Figma 母版的同步流程見 `references/母版同步指南.md`。
>
> **版本註**：v2（2026-08-01）依實測回饋大改。v1 用 `group` 當分類容器，導致標題與元件只有座標關係、且 `group` 不支援任何繪圖屬性；v2 改用 `frame`。若你看到的 `.pen` 還是 v1 的 group 結構，見第 10 節的遷移說明。

## 0. 動手前的三件事

1. **讀既有變數**：`GetVariables()` 或 `get_app_state`，確認 `$surface-2`／`$ink`／`$r-sm`／`$font-tc` 這些變數在**這一份檔案**裡真的存在。各檔變數表不一致，引用不存在的變數會被**靜默丟棄**（不報錯），寫完要 `Get` 讀回才知道有沒有生效。本技能第 2、3 節的樣板寫的是**來源專案** `共用元件.pen` 的變數名，**不是通用值**。
2. **盤點既有元件**：`Get` 文件根目錄，列出所有 `reusable:true` 的節點與目前位置。這個數字要留著——第 9 節的對帳檢查要用。
3. **確認畫布落點**：元件庫佔用畫布的哪一區。沒有前例時自己選一個明確的起點（例如 `x:1940`），並在回報中講明，不要讓元件庫跟殘留內容「剛好不重疊」而已。

## 1. 核心原則：分類＝一個 frame，標題與元件都是它的子節點

```
分類 frame（layout:"vertical", gap:12）
├─ 標題 frame
├─ row frame（layout:"horizontal", gap:40）→ 第 1 列元件
├─ row frame（layout:"horizontal", gap:40）→ 第 2 列元件
└─ ...
```

**為什麼是 frame 不是 group**（v1 踩過的坑，別再踩）：

| | `type:"group"` | `type:"frame"` |
| --- | --- | --- |
| `fill`／`stroke`／`cornerRadius` | **不支援** | 支援 |
| `layout`／`gap`／`padding` | **不支援**（純座標容器，子節點要自己算 x/y） | 支援 |
| 標題與元件的關係 | 只能靠 y 座標相鄰，**任何人拖一下就對錯** | 同一個父節點的子節點，結構上綁死 |

分類要是**節點樹的結構**，不是座標上的默契。用 `group` 就只能得到後者。

**附帶效果**：改用 frame 之後，第 4 節的網格由 `layout`＋`gap` 自動排出來，**不需要手算任何 x/y**——v1 那些「x[k] = x[k-1] + w[k-1] + 40」的算術（以及算錯 32px 的機會）整個消失。

## 2. 分類判準

### 8 類

| 分類 frame | 判準（一句話） | 範例 |
| --- | --- | --- |
| `分類-按鈕` | 使用者點擊以觸發動作 | BtnPrimary、BtnGhost、BtnDanger |
| `分類-輸入` | 使用者輸入或選取資料 | Field、SearchInput、Dropdown、Textarea、Dropzone、RadioCard、Segmented |
| `分類-狀態標籤` | 表達單一狀態／布林值的小型符號 | StatusPill、Badge、Chip、Toggle、Checkbox、Radio |
| `分類-版面容器` | 包住其他內容的框架 | Table、Modal、ConfirmDialog、TabPanel、StatCard |
| `分類-列表列項` | 清單／導覽中重複出現的一列 | TableRow、MasterListItem、NavItem、NavGroup、ToggleRow |
| `分類-頁首操作列` | 頁面級的橫條操作區 | PageHeader、Filter、BatchBar、Pagination、Stepper |
| `分類-回饋提示` | **由系統狀態觸發**、非使用者操作的訊息呈現 | Tooltip、Callout、InfoNote、EmptyState |
| `分類-其他` | 前七類都套不上 | Timeline、StatBar、Thumbnail、KVRow |

### 判準衝突時的裁決順序（依序套用，第一個能判定的就定案）

多數元件同時符合兩類以上，**這是分類軸線本身不統一造成的**（按鈕／輸入是語意軸、版面容器／列表列項是形狀軸、頁首操作列是位置軸），不是你判斷力的問題。用固定順序裁決，讓不同人做出同樣的結果：

1. **能不能被使用者直接操作？** 能 → 依「操作的性質」進按鈕／輸入／狀態標籤。不能（純呈現）→ 進版面容器／回饋提示／其他。
   - **三個子類都不精確符合時不要硬塞**，繼續走第 2 步。實測反例：`DragHandle 拖曳把手`確實可被操作，但它既不是按鈕也不是輸入或狀態符號，硬歸按鈕會讓它跟 `BtnPrimary` 並列、看起來像分類錯誤。誠實地落到 `分類-其他` 比勉強歸類好。
2. **是不是由系統狀態觸發的訊息？** 是 → `分類-回饋提示`（優先於「它長得像個容器」）。
3. **是不是清單裡重複出現的一列？** 是 → `分類-列表列項`（優先於「它裡面包了東西」）。
4. **是不是頁面級的橫條？** 是 → `分類-頁首操作列`。欄位級的工具列（如 RichTextToolbar）**不算**，走第 5 步。
5. 以上都判不出來 → `分類-其他`，並在回報中列為「分類存疑」請使用者確認。

**`分類-其他` 是最後手段，不是垃圾桶。** 它的數量超過總數 15% 就代表分類架構該檢討了——回報使用者，建議新增類別，不要默默塞。

## 3. 分類標題

每個分類 frame 的**第一個子節點**是標題：

```js
{type:"frame", name:"標題", fill:"$surface-2", cornerRadius:"$r-sm",
 padding:[6,12], alignItems:"center", children:[
   {type:"text", name:"t", content:分類名, fill:"$ink",
    fontFamily:"$font-tc", fontSize:13, fontWeight:"700"}]}
```

- 變數名**先照第 0 節確認過再用**，不同檔案不一定叫這些名字。
- 標題是分類存在的證據，不是裝飾——沒有標題的一堆元件，六個月後誰都看不出來它們為什麼被擺在一起。
- 標題與第一列元件的間距由分類 frame 的 `gap` 決定（建議 12），不要另外插空白節點。

## 4. 網格排版

每列一個 row frame，元件當它的子節點：

```js
{type:"frame", name:"row-1", layout:"horizontal", gap:40, alignItems:"start", children:[...]}
```

**每列放幾個**，依該列最寬元件決定：

| 該列最寬元件 | 每列上限 |
| --- | --- |
| ≤ 200px | 5 個 |
| 201～600px | 3 個 |
| > 600px | 2 個 |

沒有這條門檻，`分類-頁首操作列` 一列排 5 個 1180 寬的元件會讓分類 frame 寬達 5600px，把畫布橫向拉到不可讀（v1 實測後果）。

- `gap` 全庫統一（建議 40），**同一份檔案內不要有第二個值**。
- `alignItems:"start"` 讓同列高度不一的元件上緣對齊；要置中對齊就全庫統一用 `center`，不要混用。
- 分類 frame 用 `layout:"vertical"` + `gap:12`，列與列的間距由它決定。

## 5. 分類之間的間距

分類 frame 之間的間距是**畫布層級的座標**（分類 frame 是文件根目錄的頂層節點），需要手動設定，有兩條路線：

| 路線 | 分類間距 | 適用 | 前提 |
| --- | --- | --- | --- |
| 留白分隔 | ≥ 分類內 `gap` 的 3 倍 | 元件多、要長時間瀏覽盤點 | 無 |
| 緊湊排列 | ≤ 分類內 `gap` | 省畫布空間 | **分類 frame 必須有 `fill` 或 `stroke`**，否則分類邊界會消失 |

**絕對值一律問使用者，不要預設。** 沒有偏好時採「留白分隔」，並說明理由。

> v1 寫「量級差異」是錯的描述——不可判定，而且拿來舉例的 64 vs 120 自己就不到 2 倍。改用上表的比值判準。
>
> 來源專案的 `共用元件.pen` 採**留白分隔（120px）**＋分類 frame 的 1px 淡框（`$card-line`）。
>
> 演進紀錄（2026-08-01 同日）：先試 **5px 緊湊排列**，實際看過版面後改為 **120px**——使用者的回饋是「frame 之間太貼近」。**教訓：緊湊路線在紙上成立（有淡框當邊界就夠），但分類 frame 高度差距大時（該檔 104～1359px），5px 會讓高矮分類擠成一團、讀起來像同一區。分類尺寸落差大時優先選留白分隔。**

## 6. 命名慣例

- **分類 frame**：`分類-{類名}`（例：`分類-按鈕`）。**全庫一套前綴就好**——v1 同時有 `G-` 和 `區段-` 兩套前綴指同一件事，是混亂來源。
- **row frame**：`row-{序號}`。
- **元件**：`{英文名} {中文名}`（沿用專案既有慣例，例：`BtnPrimary 主要按鈕`）。
- **變體實例**：`{元件名} · {變體名}`，**變體名一律大寫開頭**（`Danger` 不是 `danger`、`Hover` 不是 `hover`）。
- **不要縮寫到看不出原意**：Figma 母版出現過 `Property 1=ter`（應為 `Tertiary`），跟旁邊標籤對不上。寧可打完整詞。
- **多狀態元件的行列標籤要另外用文字節點標出來**（「樣式：Primary／Secondary／Danger」「狀態：Enabled／Hover／Disabled」），不要要求看的人展開節點去猜屬性值。

## 7. 變體 vs 示範實例：界線與落點

這兩者長得像，但角色不同，**混在一起會稀釋分類的意義**：

| | 定義 | 放哪 |
| --- | --- | --- |
| **元件本體** | `reusable:true` 的節點 | 對應的分類 frame 內 |
| **變體展示** | `ref` 指向元件本體、用 `descendants` 覆寫出不同狀態／樣式 | 獨立的「變體示意」分類 frame，**不要**混進元件本體的分類 |
| **用法示範** | 畫面內文裡示範元件被用起來的樣子（如某張畫面表格裡的示範列） | 留在它所屬的畫面裡，**不進元件庫** |

判斷方式：看它是不是 `type:"ref"`。是 `ref` 且獨立存在於根目錄 → 變體展示。是 `ref` 但巢狀在某個畫面 frame 內 → 用法示範。

**漏網之魚**：有些變體展示是**手繪的**（不是 `ref`、也不 `reusable`），例如把三顆不同數字的 Badge 並排畫成一個 frame。這種節點**兩邊都不歸**，會在第 9 節第 1 項的對帳中完全隱形（對帳只數 `reusable`）。因此：

- 名稱含「變體」／「示意」／「Variants」的根目錄 frame，即使不是 `ref`，一律視為變體展示。
- 第 9 節第 1 項對帳時，**額外列出「既非 `reusable`、又不是分類 frame」的根目錄節點**清單，逐一確認它們的去向，不要讓它們默默留在畫布上變成孤兒。

「變體示意」frame 的結構與一般分類相同（標題＋row frames），只是內容全是 `ref`。

## 8. 殘留內容的辨識與處理

`.pen` 元件庫的殘留長什麼樣（**不是** Figma 那種灰底草稿區，v1 照抄 Figma 的判準是錯的）：

- **孤兒標題 frame**：底下已經沒有任何元件的舊分類標題（重新分類後最常見）。
- **舊座標的 ref 實例**：分類重排時沒跟著搬的變體展示，散在舊區塊。
- **重複的同名元件**：同一個元件被畫了兩次，一個在分類內、一個在外面。

**處理規則**：辨識出來後**先列清單問使用者**，不要自行刪除。刪除任何節點前必須確認**沒有其他節點 `ref` 指向它**——共用元件被引用的範圍可能跨檔案，刪了會讓其他畫面斷鏈。

## 9. 驗證

同 [[pen-authoring]] 第 10 節，元件庫額外加驗這六項。**一律以 `execute` 的 `Get` 讀回值為準；截圖與 `Get` 不一致時信 `Get`**（部分環境的 Pencil 有 render stale 問題）。

> ⚠️ **`execute` 的回傳反映呼叫過程中的中間狀態，不是最終狀態。** 兩個實測案例：
>
> - 同一次呼叫裡 `Update(y)` → `Get(bounds)`，拿到的是變更**前**的高度；另起一次呼叫再讀才是真值。
> - 同一次呼叫裡 `Delete(id)` 之後，issues 清單仍回報**該已刪節點**的 collapsed size 警告；下一次呼叫確認該節點根本不存在。
>
> 所以：**凡是「改完要驗」的動作，一律拆成兩次 `execute`**（讀現況 → 寫入 → 另起一次讀回驗證）。這不是偶發的 render stale，是穩定可重現的行為——實測把讀寫拆開後完全不再遇到數值錯亂。把中間狀態的警告當成真問題去「修」，只會白忙一場。

1. **元件總數對帳**：各分類 frame 內的 `reusable` 子節點數合計 == 全檔 `reusable:true` 總數。這是唯一能確認「沒有元件漏在分類外」的檢查。同時列出「既非 `reusable`、又不是分類 frame」的根目錄節點（見第 7 節的漏網之魚）。
2. **標題就位**：每個分類 frame 的第一個子節點是標題 frame，且內容文字 == 分類名。
3. **每列數量合規**：每個 row frame 的子節點數 ≤ 第 4 節表格依該列最寬元件算出的上限。
4. **命名掃描**：全檔掃 `/(·|-)\s*[a-z]/`，抓出小寫開頭的變體名（第 6 節規則的稽核手段）。
5. **無重疊**：文件根目錄所有頂層節點兩兩矩形碰撞，`overlap` 必須為 0。
6. **無 clip 截斷**：分類 frame 若設了固定寬高，確認內容沒被切掉（`clip` 的內容不會報錯，只會消失）。

> **不要驗「同一欄 x 相同」**（v1 的錯誤條款）。元件寬度差距可達 30 倍（`Table` 1180 vs `Toggle` 40），欄位對齊在這種元件庫恆為假，照驗會把全部分類判成不合格。改用 frame 的 `layout` 之後，列內對齊由引擎保證，本來就不需要人工驗。

**完成後明確提醒使用者手動 Save All** —— `.pen` 的鐵律是 worker 不自行存檔，改動只存在編輯器記憶體。

## 10. 從 v1（group 結構）遷移

若檔案目前是 v1 的 `type:"group"` 分類：

1. 對每個 group，建一個同名的 `frame`（`layout:"vertical"`, `gap:12`），放在 group 原本的座標。
2. 建標題 frame 當第一個子節點。
3. 依第 4 節的每列上限，建 row frames，把原 group 內的元件 `Move` 進去。**用 `Move` 不要重畫**——重畫會產生新 ID，斷掉其他畫面的 `ref` 引用。
4. **元件 `Move` 進 row frame 後，必須 `Update(id, {layoutPosition:"auto"})`。** 這是本遷移最大的坑，漏了會以為元件全部消失：
   - `group` 是純座標容器，它的子節點全都帶著 `layoutPosition:"absolute"`；`Move` 會**完整保留**這個屬性。
   - 後果：元件以絕對定位待在 row frame 裡、**被排除在 flex 流之外**，row 沒有任何「在流內的子節點」可撐開尺寸。
   - 更麻煩的是引擎會**把塌陷固化**——自動把 row 的 `width`/`height` 改寫成 `fit_content(0)`。所以修好 `layoutPosition` 之後，還要**一併把 `width`/`height` 重設回 `"fit_content"`** 才會恢復。
   - 症狀：分類 frame 讀回來的寬度只有標題那麼寬（100～150px），元件全被標記 `fully clipped`。
   - 殘留的 `x`／`y` 反而只是雜訊（flex 子節點會忽略），順手清掉即可，不是重點。
5. **立刻另起一次 `execute`，`Get` 讀回每個分類 frame 的 `bounds.width`**，確認不是只有標題寬。**這一步要在刪除舊 group 之前做**——先刪就沒有退路了。
6. 確認原 group 已空，刪除它。
7. 跑第 9 節的六項驗證，特別是第 1 項對帳——遷移最容易漏元件。
